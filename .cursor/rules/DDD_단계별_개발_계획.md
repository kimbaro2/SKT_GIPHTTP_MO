# 도메인 주도 개발(DDD) 단계별 개발 계획

## 전제
- **설계 기준**: `ESMClass_서비스_리팩토링_규칙.mdc`, `통계_과금_ESMClass별_설계.md`를 따른다.
- **핵심**: `service/mo/impl` 하위 핸들러가 운용의 중심이며, DDD는 이 구조를 유지·강화하는 방향으로 적용한다.
- **목표**: 유지보수성·운영 이점을 위해 레이어와 책임을 명확히 하고, 도메인 용어를 정립한다.

---

## 1단계: 도메인 용어 및 경계 정립 (Bounded Context 식별)

### 1.1 목표
- MO 처리의 **핵심 도메인 개념**을 문서·코드에 명시한다.
- 나중에 Entity/Value Object로 옮길 **후보**를 정리한다.

### 1.2 작업 내용
| 항목 | 내용 |
|------|------|
| **유비쿼터스 언어 정리** | ESMClass, MoServiceType, destCID, QITEM, 번호규칙(1584·638·2580·#), MOTRBILL, InsqStat, bprintf 등 용어를 한 문서에 정의. |
| **Bounded Context 후보** | (1) **MO 수신·라우팅**: ESMClass 분기, 번호규칙, 서비스 타입 결정. (2) **MO 처리·과금**: 핸들러별 처리, 통계·과금 호출. (3) **MO 전송(MO-TR)**: 전송 결과 처리, MOTRBILL. |
| **산출물** | `.cursor/rules/DDD_유비쿼터스_언어.md` (또는 기존 규칙 문서에 섹션 추가). |

### 1.3 완료 기준
- 신규/기존 개발자가 “ESMClass”, “MoServiceType”, “1584 불변성” 등을 문서만 보고 이해할 수 있다.
- Bounded Context 후보가 코드 구조(패키지/클래스)와 1:1로 매핑 가능한 수준으로 기술되어 있다.

---

## 2단계: 도메인 레이어 폴더·패키지 구조 도입 *(건너뜀 — 현재 구조로 충분)*

> **결정**: 2단계는 수행하지 않음. 기존 `service/handler`, `service/mo/impl` 구조를 유지한다.

### 2.1 목표
- **domain** 패키지를 두고, 인프라/애플리케이션과 구분되는 “도메인만의” 코드 위치를 만든다.
- 기존 `service/handler`, `service/mo`는 유지하되, **도메인 개념이 들어갈 자리**만 먼저 확보한다.

### 2.2 제안 패키지 구조
```
com.infra.mo.skt_giphttp_mo/
  domain/                    # 신규
    mo/                      # MO 수신·라우팅·처리 도메인
      MoServiceType.kt       # (기존 handler에서 이동 검토) 서비스 타입 enum
      EsmClass.kt            # (선택) ESMClass 값 객체 또는 상수
      NumberRule.kt          # (선택) 번호규칙 불변성: 1584, #, 638, 2580 등
    billing/                 # (선택) 과금·통계 도메인
      BillType.kt            # 기존 utils 등에서 도메인 의미만 정리
  application/               # (선택, 3단계에서 명시)
    mo/
      MoServiceHandler.kt    # 핸들러 인터페이스
      MoServiceContext.kt    # 처리 컨텍스트
  service/
    handler/                 # 기존 유지. domain/application과 연동
    mo/impl/                 # 기존 유지. Application Service 역할 명시
  config/
  db/
  ...
```

### 2.3 작업 내용
- `domain/mo` 패키지 생성.
- **MoServiceType**을 `service/handler` → `domain/mo`로 이동할지 결정 (이동 시 `MoServiceTypeResolver`, `MoServiceHandlerRegistry` 등 참조 경로 수정).
- **EsmClass**, **NumberRule** 등은 필요 시 Value Object로 추가 (1단계 용어 정리 결과 반영).
- `통계_과금_ESMClass별_설계.md`와 충돌 없이 “비즈니스 로직은 호출 클래스(핸들러) 내부” 원칙을 유지한다.

### 2.4 완료 기준
- `domain` 패키지가 존재하고, MO 서비스 타입·번호규칙 등 **도메인 개념**이 여기서 한 곳에 정의되거나, 기존 코드와의 매핑이 문서로 정리되어 있다.

---

## 3단계: 애플리케이션 서비스(핸들러) 역할 명시

### 3.1 목표
- `service/mo/impl`의 각 핸들러를 **Application Service**로 명확히 하고, “도메인 로직 호출 + 인프라 위임”만 하도록 책임을 고정한다.

### 3.2 작업 내용
| 항목 | 내용 |
|------|------|
| **인터페이스 정리** | `MoServiceHandler.handle(qItem, context)`가 Application Service의 진입점임을 주석/문서에 명시. |
| **핸들러 내부 원칙** | (1) ESMClass·MoServiceType에 따른 **분기/검증** (2) **도메인 서비스** 또는 **도메인 규칙** 호출 (3) 인프라(DB, JNA, HTTP, InsqStat 등) 호출은 서비스/유틸에 위임. |
| **MoServiceContext** | “도메인·인프라가 섞인 처리 컨텍스트”로 정의하고, 필요 시 `application/mo`로 이동 검토. |

### 3.3 완료 기준
- 각 핸들러가 “이 서비스 타입의 MO를 처리하는 Application Service”라고 한 문장으로 설명 가능.
- ESMClass_서비스_리팩토링_규칙.mdc의 “분기부는 분기+핸들러 호출만, 구체 로직은 서비스별 클래스”와 일치한다.

---

## 4단계: 도메인 서비스·도메인 로직 추출 *(건너뜀)*

> **결정**: 4단계는 수행하지 않음. 번호규칙·1584·MOTRBILL 판단은 현재 위치(핸들러·MoServiceTypeResolver·MoBillTypeService 등)에 유지한다.

### 4.1 목표
- 핸들러 안에 흩어진 **번호규칙 검증**, **1584 불변성 검증**, **MOTRBILL 판단** 등을 **도메인 서비스** 또는 **도메인 규칙 클래스**로 추출한다.
- “공용동작로직영역에는 비즈니스로직을 두지 않는다”는 통계·과금 설계와 조화시킨다. (판단·분기는 호출 클래스/핸들러, 공용은 유틸/인프라만.)

### 4.2 작업 내용
| 항목 | 내용 |
|------|------|
| **번호규칙(불변성)** | “앞자리 1584”, “맨 뒤 #”, “638/2580” 등이 **도메인 규칙**으로 문서화되고, 가능하면 `domain/mo/NumberRule` 또는 `MoServiceTypeResolver`와 연동된 한 곳에서만 판단. |
| **1584 검증** | NormalMoHandler에서 수행하는 “앞자리 1584” 검증을 `domain/mo`의 도메인 서비스 또는 정적 메서드로 추출 (위치: NormalMoHandler 내부 private 유지 가능, 도메인 패키지에 규칙 클래스만 두고 핸들러가 호출). |
| **MOTRBILL** | `MoBillTypeService.isMoTrBillEnabled` 등이 **도메인 정책**에 해당함을 명시하고, 필요 시 `domain/billing`에 인터페이스만 두고 구현은 기존 서비스에 유지. |

### 4.3 완료 기준
- 번호규칙·1584·MOTRBILL 판단이 “도메인 규칙/도메인 서비스”로 명명되어 있고, 핸들러는 그를 호출하는 쪽으로만 동작한다.
- 통계·과금 설계의 “호출 클래스 내부에 분기”는 유지되며, “무엇을 판단할지(규칙)”는 도메인 레이어에 모인다.

## 5단계: 인프라 의존성 방향 정리 (DIP)

### 5.1 목표
- **도메인·애플리케이션**이 DB, JNA, HTTP, 로깅 등 **인프라에 직접 의존하지 않도록** 인터페이스(포트)를 두고, 구현(어댑터)은 인프라 쪽에 둔다.

### 5.2 원칙: 각 도메인별 의존 주입
- **사전에 호출하지 않더라도** 각 도메인(핸들러·서비스 타입별)에서 **의존 주입은 수행한다**.
- 해당 유스케이스에서 실제로 호출되지 않는 포트/서비스라도, 그 도메인이 필요로 할 수 있는 의존은 생성 시점에 주입해 둔다. (실제 호출 여부는 처리 흐름에 따라 결정.)

### 5.3 작업 내용
| 항목 | 내용 |
|------|------|
| **포트 정의** | 예: MO 전송 결과 저장, Access Entity 조회, 통계 전송(InsqStat), 과금(bprintf) 등에 대한 **인터페이스**를 application/domain 쪽에 정의. |
| **어댑터** | 기존 `MoTrSendService`, `Mo1584EntityResolveService`, DB 레포지토리, JNA 래퍼 등을 **인프라 구현체**로 두고, 핸들러는 인터페이스만 참조. |
| **의존 주입** | 각 도메인(핸들러)은 사용 여부와 관계없이 **필요한 의존을 모두 주입받는다**. 호출은 분기·조건에 따라 선택적으로 수행. |
| **점진적 적용** | 한 번에 모든 서비스를 바꾸지 않고, **새로 추가되는 기능**이나 **변경 빈도가 높은 부분**부터 포트/어댑터를 도입. |

### 5.4 완료 기준
- 최소 한 개의 유스케이스(예: MO-TR 처리 또는 1584 entity 조회)가 “도메인/애플리케이션 → 인터페이스 ← 인프라 구현” 구조로 동작한다.
- 각 도메인(핸들러)은 사전 호출 여부와 관계없이 필요한 의존을 주입받도록 구성되어 있다.
- 기존 ESMClass·핸들러 구조는 유지된다.

## 6단계: 문서·규칙 동기화 및 유지보수 *(완료)*

### 6.1 목표
- DDD 레이어·용어가 **ESMClass_서비스_리팩토링_규칙.mdc**, **통계_과금_ESMClass별_설계.md**와 일치하도록 문서를 갱신한다.
- 새 ESMClass/서비스 타입 추가 시 따라갈 **체크리스트**에 DDD 항목을 넣는다.

### 6.2 작업 내용
| 항목 | 내용 |
|------|------|
| **규칙 문서 보강** | ESMClass 규칙에 “도메인 레이어”, “Application Service(핸들러)”, “인프라” 용어와 역할 한 줄씩 추가. |
| **체크리스트** | “새 서비스 타입 추가 시: MoServiceType 추가 → 핸들러 추가 → MoServiceTypeResolver 분기 추가” 순서 명시. |
| **1584 불변성** | “1584는 NormalMoHandler 검증을 통한 불변성”이 DDD 관점에서는 **도메인 규칙(NumberRule)**에 해당함을 문서에 명시. |

### 6.3 완료 기준
- DDD_단계별_개발_계획.md, ESMClass_서비스_리팩토링_규칙.mdc, 통계_과금_ESMClass별_설계.md를 함께 읽었을 때 설계가 일관되게 보인다.
- 운영·유지보수 시 “도메인 규칙은 어디를 고치나”, “핸들러는 무엇을 담당하나”가 문서에서 바로 답할 수 있다.

## 요약: 단계별 순서

| 단계 | 이름 | 핵심 산출물 |
|------|------|-------------|
| **1** | 도메인 용어·경계 정립 | 유비쿼터스 언어 문서, Bounded Context 후보 |
| **2** | 도메인 레이어 패키지 도입 | *(건너뜀 — 현재 구조로 충분)* |
| **3** | 애플리케이션 서비스(핸들러) 역할 명시 | 핸들러 = Application Service 문서·주석 |
| **4** | 도메인 서비스·도메인 로직 추출 | *(건너뜀)* |
| **5** | 인프라 의존성 방향 정리 (DIP) | 포트/어댑터 1개 이상 적용 |
| **6** | 문서·규칙 동기화 | 규칙 문서·체크리스트에 DDD 반영 *(완료)* |

- **1→3**은 구조와 역할 정리 위주로, 기존 코드 대규모 이동 없이 진행한다. (2단계는 건너뜀.)
- **5**는 리팩토링이 조금씩 들어가므로, 한 번에 한 서비스 타입/한 유스케이스씩 적용하는 것을 권장한다. (4단계는 건너뜀.)
- **6**은 각 단계 완료 시마다 부분 반영해도 된다.

이 계획은 **ESMClass_서비스_리팩토링_규칙.mdc**의 설계를 따르며, **1584는 NormalMoHandler.kt 검증을 통한 앞자리 1584 불변성**으로 두고, **mo/impl 핸들러를 운용의 핵심**으로 유지한 채 DDD를 단계적으로 도입하는 내용이다.
