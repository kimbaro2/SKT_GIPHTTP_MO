# 순환 의존성 수정 후 시스템 안정성 검토

## 1. 적용된 수정 요약

| 구분 | 파일 | 변경 내용 |
|------|------|-----------|
| 순환 끊기 | MoDbInsertServiceImpl | 생성자에서 `SmsResService`에 `@Lazy` 적용 |
| CGLIB 호환 | MoDbInsertServiceImpl | `open class` + `@Transactional` 메서드 `open override` |

---

## 2. 안정성 검토 결과

### 2.1 빈 생성·초기화 순서 (안정)

- **순환 제거**: MOThreadPool → Registry → Handlers → **MoDbInsertServiceImpl** → (지연) SmsResServiceImpl → …  
  → `MoDbInsertServiceImpl` 생성 시 `SmsResService`는 프록시로 주입되므로 컨텍스트 생성 시점 순환 없음.
- **초기화 순서**: 컨텍스트 완료 후, `insertGIPMOCallInfo` 등 최초 호출 시 프록시가 실제 `SmsResServiceImpl`을 resolve. 이 시점에는 모든 빈이 이미 생성되어 있어 NPE/미초기화 위험 없음.

### 2.2 @Lazy 동작 (안정)

- Spring의 `@Lazy` 프록시는 **첫 메서드 호출 시** 실제 빈을 한 번만 resolve하고 이후 재사용.
- **스레드 안전**: DefaultListableBeanFactory 기준으로 싱글톤 조회는 스레드 세이프하므로, 다중 스레드(MOThreadPool 워커 등)에서 동시에 `smsResService.insertGIPMOCallInfo()`를 호출해도 동일 인스턴스가 안전하게 사용됨.
- **호출 경로**: Handler → `moDbInsertService.insertGIPMOCallInfo()` → `smsResService.insertGIPMOCallInfo()` → (프록시 경유) `SmsResServiceImpl.insertGIPMOCallInfo()`. 동작 변화 없음.

### 2.3 트랜잭션 경계 (안정)

- **MoDbInsertServiceImpl**
  - `insertGIPMOCallInfo`: 트랜잭션 없음, 곧바로 `smsResService.insertGIPMOCallInfo()` 위임.
  - `insertMO_NOTISEND` / `insertRelayMOCallInfo`: `@Transactional` 유지, CGLIB으로 프록시 생성되므로 기존과 동일하게 트랜잭션 적용.
- **SmsResServiceImpl.insertGIPMOCallInfo**
  - `@Transactional(Propagation.REQUIRES_NEW)` 유지.
  - 위임 호출은 프록시를 타므로 Spring이 정상적으로 새 트랜잭션을 열어 동작. 수정 전/후 트랜잭션 의미 동일.

### 2.4 open class / open override (안정)

- **open class**: CGLIB이 `MoDbInsertServiceImpl`을 상속해 `@Transactional`용 프록시 생성 가능.
- **open override**: `insertMO_NOTISEND`, `insertRelayMOCallInfo`만 오버라이드 가능하게 열어, 프록시가 트랜잭션 경계를 적용. 다른 메서드는 그대로 final로 두어 의도치 않은 오버라이드 방지.
- `insertGIPMOCallInfo`는 위임만 하므로 트랜잭션 불필요 → open 미적용으로 유지.

### 2.5 사용처 일관성 (안정)

- **MoDbInsertService** 사용처: MOThreadPool, NormalMoHandler, NotiPlusHandler, NotiRegisteredHandler, ForwardHandler, CdmaRoamingHandler, GsmRoamingHandler, Character1584Handler, SmsMessenger2580Handler, SmsManager638Handler, MoSmReqSimpleProcessServiceImpl.
- 모두 `moDbInsertService.insertGIPMOCallInfo` / `insertMO_NOTISEND` / `insertRelayMOCallInfo`만 호출하며, 인터페이스 계약과 반환값·예외 동작은 수정 전과 동일.

## 3. 잠재 리스크 및 권장 사항

| 항목 | 수준 | 내용 | 권장 |
|------|------|------|------|
| 첫 호출 지연 | 낮음 | `smsResService` 최초 사용 시 한 번만 빈 resolve. 체감 지연 무시 가능. | 별도 조치 불필요. |
| 디버깅 시 스택 | 낮음 | `@Lazy` 프록시 경유 시 스택에 프록시가 한 단계 더 보일 수 있음. | 필요 시 “Step Over”로 실제 구현으로 진입. |
| 장기 구조 개선 | 참고 | 순환 제거는 유지하되, 향후 `insertGIPMOCallInfo` 로직을 MoDbInsertServiceImpl 쪽으로 이전하면 MoDbInsertService → SmsResService 의존 제거 가능. | 리팩터 시 검토. |

---

## 4. 결론

- **기동**: 순환 의존성 제거로 정상 기동 가능.
- **런타임**: `@Lazy`·트랜잭션·open 변경으로 인한 동작 차이 없음. 다중 스레드·호출 경로·트랜잭션 경계 모두 수정 전과 동일한 수준으로 유지됨.
- **유지보수**: Kotlin + Spring 조합에서 흔히 쓰는 방식(@Lazy + open class/메서드)에 맞춰져 있어, 추가 모니터링 없이 운영 가능한 수준으로 판단됨.

**권장**: 기동·단위/통합 테스트 후, MO 정상 수신·DB 적재·과금/통계 플로우만 스모크 확인하면 안정성 검토 완료로 보는 것이 적절함.
